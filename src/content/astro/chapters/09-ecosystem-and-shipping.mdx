Eight chapters built the mental model: HTML first, islands where they pay, content with a schema, rendering as a dial. What remains is everything around the code — the integrations that save you from writing the boring half of every site, the docs theme that makes you look more professional than you feel, and the pipeline that turns `git push` into a deployed, measured, monitored site. This chapter tours the ecosystem, then assembles the production checklist. Launch is not a vibe; it is a list, and the list is short because Astro made most of the hard items default behavior.

## The ecosystem map

Astro's core is deliberately small, and the ecosystem carries the rest through *integrations* — packages that hook into the build to add a capability. The catalog covers the predictable ground: `@astrojs/mdx` (already load-bearing in Chapter 4), sitemap generation, icons, image tooling, and the framework integrations from Chapter 5. Installing one is a one-liner that edits your config for you:

```bash
npx astro add mdx sitemap partytown
```

That command installs the packages, wires them into `astro.config.mjs`, and tells you what it changed — the closest thing the JavaScript ecosystem has to `cargo add` behaving predictably. The mental model to hold: the core renders and routes; integrations extend the build; adapters (Chapter 6) teach the output to run somewhere. When you evaluate a third-party capability, the first question is which of those three shapes it takes, because it determines whether the feature costs runtime bytes or build-time work — the same budget discipline the whole book has applied, now applied to the ecosystem.

## Starlight for documentation

Documentation is the use case Astro's ecosystem handles best, and *Starlight* is the reason: a documentation theme that generates a full docs site from content collections. You already know the machinery underneath — your markdown becomes a collection, the schema gains docs-specific fields, and the theme supplies the rest:

```js
// astro.config.mjs
import { defineConfig } from "astro/config";
import starlight from "@astrojs/starlight";

export default defineConfig({
  integrations: [
    starlight({
      title: "Orbit Docs",
      sidebar: [
        { label: "Getting started", slug: "getting-started" },
        { label: "API", autogenerate: { directory: "api" } },
      ],
      locales: {
        en: { label: "English" },
        de: { label: "Deutsch" },
      },
    }),
  ],
});
```

What the theme brings is everything you would otherwise build badly: sidebar navigation with autogenerated sections, internationalization with translated UI strings, keyboard-accessible search (Pagefind, indexing the built site client-side), code blocks with copy buttons, and next/prev pagination. The value proposition is the one `cargo doc` taught the Rust world: documentation that is cheap to maintain stays maintained. Starlight costs an afternoon to stand up and repays it the first time someone finds the answer via built-in search instead of asking you.

## Integrations worth knowing

Beyond Starlight, a short list earns its keep on almost every content site. `@astrojs/sitemap` generates a `sitemap-index.xml` from your routes at build — set `site` in the config and forget it. RSS is a small helper library away, and a changelog that offers a feed is a changelog people actually follow. Icons ship through `astro-icon`, which inlines SVGs from an icon set at build time with zero client cost. And partytown, met in Chapter 5, belongs in the config of any site with third-party analytics:

```js
// astro.config.mjs
import { defineConfig } from "astro/config";
import sitemap from "@astrojs/sitemap";

export default defineConfig({
  site: "https://example.com",
  integrations: [sitemap()],
});
```

The selection principle from the ecosystem map applies down the list: prefer integrations that work at build time, because they keep the zero-JS budget intact. A sitemap generated during the build costs nothing at request time; a client-side sitemap generator would be absurd, and most categories have both kinds of option. Read the integration's mechanism, not just its feature list — the good ones are the ones you cannot detect in the network tab.

## Performance budgets and audits

Astro's defaults put you near the top of the Lighthouse leaderboard, but "fast by default" is not a budget — a budget is a number you refuse to cross, written down before launch. The honest version is three lines: total page weight, JavaScript bytes, and Largest Contentful Paint on a throttled connection. Islands make the JavaScript line easy to reason about, because each island's cost is visible and local; images are the line that drifts, which is why Chapter 7's `astro:assets` pipeline is worth its setup cost. Measure with Lighthouse in Chrome, and enforce with Lighthouse CI so regressions arrive as failed checks rather than vibes:

```yaml
# lighthouserc.yml
ci:
  collect:
    numberOfRuns: 3
    staticDistDir: ./dist
  assert:
    assertions:
      categories:performance: ["error", { minScore: 0.9 }]
      total-byte-weight: ["error", { maxNumericValue: 500000 }]
```

Run against `dist` — the static output makes that possible — with multiple runs to smooth variance. The assertions fail the pipeline when the budget breaks, which converts performance from a launch-week panic into a gate that runs on every change. A budget you enforce in CI is a promise; one you check "sometimes" is a mood.

## Testing an Astro site

Testing splits along the rendering model. Pure functions — the utilities in `src/lib`, schema transformations, query filters — are ordinary TypeScript, and vitest covers them without any Astro involvement:

```ts
// src/lib/search.test.ts
import { describe, expect, it } from "vitest";
import { searchPosts } from "./search";

describe("searchPosts", () => {
  it("matches titles case-insensitively", () => {
    const results = searchPosts(fixtures, "ASTRO");
    expect(results.map((r) => r.id)).toContain("islands-explained");
  });
});
```

The pages themselves are best tested as a built site: run `astro build && astro preview`, and let Playwright drive a real browser against it. This catches what unit tests cannot — that `getStaticPaths` produced the routes, that the layout wires the navigation, that the island hydrates:

```ts
// tests/blog.spec.ts
import { test, expect } from "@playwright/test";

test("a published post renders with its byline", async ({ page }) => {
  await page.goto("/blog/islands-explained");
  await expect(page.getByRole("heading", { level: 1 })).toBeVisible();
  await expect(page.getByText("Rin")).toBeVisible();
});

test("the newsletter form validates server-side", async ({ page }) => {
  await page.goto("/subscribe");
  await page.getByLabel("Email").fill("not-an-email");
  await page.getByRole("button", { name: "Subscribe" }).click();
  await expect(page.getByRole("alert")).toBeVisible();
});
```

The second test is Chapter 8 proving itself with JavaScript deliberately left to Playwright's defaults — the action validated the input server-side, and the alert the user sees is rendered HTML. Keep the unit suite fast and the e2e suite small: a dozen well-chosen paths through the built site beats a hundred fragile ones.

## CI and deployment

Deployment splits by output mode, and the split is clean. Static output deploys as files — Netlify, Cloudflare Pages, GitHub Pages, any CDN — with the build command `npm run build` and the output directory `dist`. Request-time rendering needs the matching adapter from Chapter 6, and the host then runs the server output for you. Either way, the pipeline is the same shape:

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build
        env:
          CMS_TOKEN: ${{ secrets.CMS_TOKEN }}
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist
```

The env wiring is Chapter 6 closing the loop: secrets live in the CI provider's secret store, reach the build as environment variables, and never sit in a committed `.env`. Two habits worth adopting early: run `astro check` and the test suite in the same job as the build, so a type error blocks deploy rather than shipping; and let the host's deploy previews render every pull request, because a broken layout caught in a preview costs a comment, not a rollback.

## The launch checklist

The list, in the order that catches the most problems per minute spent. It is short, and that is the point — each line is cheap because the defaults were right:

- Set `site` in `astro.config.mjs`, verify the sitemap and canonical URLs, and confirm `404.astro` renders like a real page rather than a shrug.
- Run Lighthouse on the three heaviest pages, confirm the budget holds, and check the built HTML for islands that hydrate but never needed to.
- Exercise one form end to end with JavaScript disabled — the action path from Chapter 8 — because your most important visitors will include at least one browser you did not test.
- Wire the analytics `astro:after-swap` event if the client router is on, or accept that the numbers undercount by every navigation after the first.
- Point the CMS's deploy webhook at the pipeline, so content changes rebuild the site without a human remembering to.

Launch is the loop closing where Chapter 1 opened it: a page is a document, rendered once, served everywhere, with JavaScript admitted only where it earns its place. The same discipline suits how you already work — Svelte components from your other projects drop into these pages as islands unchanged, and the Rust and Tauri toolchain is waiting when a product outgrows the browser entirely. Ship it.

## Key takeaways

- The ecosystem splits into build-time integrations, runtime islands, and adapters — and build-time options keep the zero-JS budget that Chapter 1 established.
- Starlight turns your content-collection knowledge into a full docs site with search, i18n, and navigation for an afternoon of setup.
- Write budgets as CI assertions — Lighthouse score and total byte weight enforced on every change — not as launch-week intentions.
- Test in two layers: vitest for the pure logic, Playwright against `build && preview` for the routes, layouts, and server-validated forms.
- Static output deploys anywhere as files; request-time output deploys with its adapter; either way, secrets enter through CI env, never committed files.
- The launch checklist is short because the defaults were right — and the mental model holds: documents first, islands where they pay, shipped.
